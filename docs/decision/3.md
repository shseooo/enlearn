### D3-1 두 탭이 같은 저장소를 쓸 때 어떤 규칙으로 손실을 막을 것인가 (관련: R3-4)
- 위치: `src/lib/corpus.ts:201-207`(`markSeen` — 읽기→붙이기→통째 쓰기), `src/lib/corpus.ts:379-388`(`cacheKorean`), `src/lib/practice.ts:222-232`(`logPractice`), `src/lib/practice.ts:385-410`(`addForReview`), 쓰기 헬퍼 `src/lib/storage.ts`(`safeSetItem`)·`src/lib/practice.ts:74-83`(`writeArray`), 구독 `src/lib/corpus.ts:458-465`·`src/lib/practice.ts:559-572`(`storage` 이벤트)
- 배경: 모든 저장이 "전체 읽기 → 메모리에서 병합 → 전체 쓰기"라서, 탭 두 개가 열리면 A읽기→B읽기→A쓰기→B쓰기 순서로 interleaving되고 A의 쓰기가 사라진다. `storage` 이벤트 구독은 화면을 맞출 뿐 이미 날아간 쓰기를 되살리지 못한다. `safeSetItem`은 성공하므로 어디에도 실패가 표시되지 않는다. 결과: 다른 탭에서 푼 문장이 다시 나온다(seen 유실), 점수 기록 하나·SRS 항목 하나가 사라진다. 앱은 여러 창 열기를 막지 않는다(`src/app/page.tsx:39-144`).
  - 이건 D1-2(큰 저장소의 쓰기 **비용**)와 별개의 문제다. D1-2는 쓰기를 적게/작게 하는 결정이고, 여기는 동시에 쓰는 두 주체의 **승자**를 정하는 결정이다.
  - D2-1(백업 병합의 저장소별 승자 규칙)과 같은 규칙표가 필요하다. 백업 병합과 탭 간 병합이 서로 다른 규칙을 쓰면 사용자에게 설명할 수 없으므로, **세 항목(D1-2·D2-1·D3-1)을 한 번에 정하는 편이 좋다.**
- 선택지:
  - A) merge-on-write: 쓰기 직전에 원문을 다시 읽고 그 자리에서 항목 단위로 병합한다(저장소별 승자 규칙 정의 필요 — seen은 key 기준 "더 최신 시각", log는 `id|date`, srs는 현행 진척 우선, 번역 캐시는 기존 우선).
    — 장점: 락·신호 없이 단순하고, 코드 위치가 이미 읽기/쓰기 헬퍼(`readJson`/`safeSetItem`, `readArray`/`writeArray`) حول로 좁다. 탭이 몇 개든 마지막 쓰기가 "합집합"이 되므로 손실 개념이 사라진다. D2-1의 승자 규칙과 같은 표로 통합할 수 있다.
    — 단점: localStorage를 쓰기마다 두 번 읽는다(seen 3MB 원문 파싱 → D1-2의 비용 문제와 정면 충돌). 항목 단위 병합 규칙을 저장소마다 정의·테스트해야 한다. "지웠다"는 동작(초기화·replace)은 병합과 구분해야 한다(병합하면 초기화가 동작하지 않으므로 tombstone 또는 명시적 삭제 플래그가 필요하다).
  - B) 낙서 락(optimistic concurrency): 저장소에 버전 번호(또는 쓰기 시각)를 함께 두고, 읽을 때의 버전과 쓰기 직전의 버전이 다르면 다시 읽고 다시 쓴다(유한 재시도).
    — 장점: 병합 규칙을 저장소별로 새로 만들지 않아도 된다 — "마지막에 읽은 기준으로 다시 계산"이 곧 승자 규칙이 된다. 삭제·replace 의미도 자연스럽다(그 탭이 본 상태에 대해 삭제하므로). 쓰기 비용은 A보다 작다(재시도할 때만 재파싱).
    — 단점: 저장소 스키마가 `{version, payload}`로 바뀐다( 마이그레이션 필요 — D1-2의 키 분할 논의와 붙는다). 재시도 실패 시 사용자에게 알릴 경로가 필요하다(현재 저장은 실패를 삼킨다). 테스트가 늘어난다(경합 시뮬레이션).
  - C) 손실을 줄이기만 한다: 탭 간 `storage` 구독을 강화해 쓰기 직전 스냅샷을 갱신하고, 문장 받기처럼 손실이 눈에 보이는 경로(seen)만 key 단위 병합으로 바꾼다.
    — 장점: 변경 범위가 가장 작고 스키마가 그대로다. 실제로 아픈 경로(같은 문장 재출제)를 잡는다.
    — 단점: race를 없애지 못하고 확률만 낮춘다. "저장소 규칙" 결정이 미결로 남아 매번 부분 대응이 쌓인다.
- 추천: **B(버전 낙서 락)를 기본으로 하고, 승자 규칙표는 D2-1의 결정과 통합한다.**
  — 이유: A는 저장소마다 병합 규칙과 tombstone 규칙을 새로 만들어야 하고, 읽기 두 번이 D1-2(큰 저장소 비용)와 충돌한다. B는 "읽을 때 버전 → 쓸 때 확인"이라는 하나의 규칙으로 손실·삭제·교체를 모두 설명할 수 있고, 스키마 변경은 D1-2에서 이미 검토 중인 키 분할과 같은 마이그레이션으로 함께 처리할 수 있다. C는 B를 정하기 전의 임시 대응으로만 허용한다.
- 결정 시 함께 정할 것
  - tombstone/삭제 표현(초기화·`replace`·`resetSeen(lane)`가 병합에서 어떻게 "지움"으로 남는가) — A를 택하면 필수, B에서도 삭제 재적용 문제를 막아야 한다.
  - 상한 트림(MAX_SEEN/MAX_SRS/MAX_RECORDS)과 재시도의 상호 작용(두 탭이 각각 트림하면 총 개수가 상한을 넘을 수 있다).
  - 저장을 포기했을 때의 사용자 알림(현재 `safeSetItem`은 실패를 삼킨다 — 리뷰 1·2에서 유지한 결정).
  - 화면이 여러 개인 탭 내부(⚙️ 설정 + 번역 탭)는 같은 이벤트 루프이므로 손실이 없지만, 묶음 쓰기(`batchProgress`/`batchPractice)와 재시도 카운트의 관계.

### D3-2 사전 번역 원고와 worklist의 대응을 기계적으로 검증할 것인가 (관련: R3-2)
- 위치: `scripts/merge-translations.mts:100-135`(번호 확인 — 이번 사이클에 "번호 없는 원고 거부"까지 반영), `scripts/dump-untranslated.mts:27-30`(행 번호 = 자기 인덱스), `scripts/merge-translations.mts:129-147`(실제 대응은 `offset + i`)
- 배경: 이번 사이클에 ①번 없는 원고를 거부하도록 고쳤다 — 원고 중간 빈 줄 하나, 탭 대신 공백 한 칸이 모든 번역을 한 칸 어긋나게 만드는 통로였고, 어긋난 채로 `.corpus-cache/translations.json`에 들어간 뒤 다음 빌드에서 `classics.json`(사람 번역 1,400문장)으로 반영된다.
  그러나 번호가 **있어도** 구조적으로 못 잡는 경우가 남는다. 검사는 `rowNumber === offset + i`이고 실제 대응도 `offset + i`이며, `dump-untranslated.mts`는 행 번호를 자기 인덱스로 쓴다. 그래서 어떤 worklist에서든 "번호 = 위치"가 항상 성립한다. dump → 원고 작성 → **코퍼스 재빌드(worklist 재생성)** → merge 순서에서, 원고가 옛 worklist의 500~599행을 옮긴 것이라도 새 worklist의 `#500` 구간과 번호가 맞아떨어져 통과한다. 3차 리뷰가 남긴 "원고 줄 단위 교차 검증은 사람이 무작위 표본으로 확인" 상태가 그대로다.
- 선택지:
  - A) 원고 형식을 `번호\t원문 앞 단어\t번역`으로 바꾼다 — merge가 worklist 행의 `en`과 대조해 다른 줄이면 거부한다(`dump-untranslated.mts:30`이 이미 원문을 내보낸다).
    — 장점: 어긋남을 **값으로** 잡는다. 번호 체계가 통째로 어긋난 경우도 잡힌다(원문 앞 단어가 안 맞으므로). 사람이 원고를 옮겨 적을 때 눈으로 대조하게 되니 작성 중 오류도 줄어든다.
    — 단점: 원고 형식 변경 — 이미 작성된 청크(`.corpus-cache/ko/*.txt`, 커밋되지 않아 마이그레이션 도구 필요)와 사람 작업 습관을 바꿔야 한다. 앞 단어 선택 기준(첫 단어? 고유명사?)이 애매해 재작업이 생길 수 있다.
  - B) worklist 지문을 저장한다 — `dump-untranslated.mts`가 `.corpus-cache/worklist.meta.json`(줄 수 + `normalizeKey(en)` 목록 해시 + 생성 시각)을 쓰고, merge가 원고 인자에 적힌 worklist와 현재 worklist의 지문이 다르면 거부한다.
    — 장점: 형식 변경 없이 "이 원고는 지금 worklist에 대해 쓴 것이 아니다"를 잡는다. dump 직후 merge하는 정상 흐름은 그대로다. 구현이 작고 테스트하기 쉽다.
    — 단점: 원고 자체가 어느 worklist에 대해 쓰였는지 **선언**하지 않으므로, 오래된 원고를 새 worklist에 섞어 쓰는 경우(청크 재사용)는 사람이 meta를 함께 옮겨야 한다. 원문 대응을 확인하지는 않으므로, 원고 안에서 줄을 직접 섞는 오류는 여전히 못 잡는다.
  - C) 현행 유지 — 이번 사이클의 "번호 없는 원고 거부"로 끝내고, 줄 단위 검증은 사람이 무작위 표본으로 확인한다.
    — 장점: 비용·작업 없음. 1,400문장은 이미 사람이 옮긴 원고로 채워졌고, 새 원고를 쓸 때마다 표본 확인을 하는 것은 현재 절차에 기록되어 있다.
    — 단점: 어긋남이 들어가면 코퍼스와 번역 캐시에 영구로 남고 화면에 엉뚱한 참고 번역으로 보인다(D2-2의 문제와 같은 종류). 사람이 확인하는 게이트는 재현되지 않는다.
- 추천: **B를 먼저 도입하고, 원고를 새로 쓰는 다음 배치부터 A를 병행한다.**
  — 이유: B는 저장소 안의 산물(dump 산물)만 바꿔 사람 원고 형식을 건드리지 않으므로 지금 즉시 도입할 수 있고, "worklist 재생성 후 어긋난 원고"라는 가장 사고 확률이 높은 경로를 막는다. A는 값 대조라 더 강하지만 형식 변경과 재작업 비용이 있어, 다음 원고 작성 단위부터 적용하는 편이 안전하다. A+B가 되면 `audit-translations.mts`의 "중복 번역" 경고가 어긋남 2차 신호로 살아난다.
- 결정에 필요한 것: 기존 `.corpus-cache/ko/*.txt` 청크 처리(재작업 vs meta 지문 기준으로 인정), 원고의 "원문 앞 단어" 선택 규칙, worklist.meta에 담을 정보(해시 알고리즘·생성 시각·코퍼스 `generatedAt`), merge가 meta 불일치를 경고로 둘지 거부로 둘지.
