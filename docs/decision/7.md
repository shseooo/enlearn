# 결정 필요 #7

### D7-1 LLM으로 보내는 사용자 입력의 상한을 어디에, 어떤 방식으로 두는가 (관련: R7-9)

- 위치: `src/components/free-writing-tab.tsx:77-83`(길이 제한 없는 textarea) · `src/components/translation-tab.tsx:515-521`(같은 형태) · 프롬프트 조립 `src/lib/llm.ts:510`(`evaluateFreeWriting`) · `src/lib/llm.ts:530-531`(`evaluateTranslation`) · `src/lib/llm.ts:653-654`(`askFollowUp`의 컨텍스트)
- 배경: 저장소 쪽은 안전하다 — 연습 기록은 `clip()` 400자(`src/lib/practice.ts:40`, `:139-140`). 그러나 **화면 입력과 LLM 요청 본문에는 상한이 없다.** `rg maxLength src` → 0건이고, `canSubmit`/`canEvaluate`(`free-writing-tab.tsx:31-33`, `translation-tab.tsx:130-135`)는 빈 값만 본다. 사용자가 통째로 붙여넣은 수십만 자가 그대로 `messages`에 실려 프로바이더로 간다. 인젝션 문제가 아니라 **자기 지갑(요청 비용·지연)을 지키는** 문제다. 리뷰는 ① `maxLength`, ② `llm.ts`의 `clipText(text, 1_500)`를 제안했지만, 두 자리에 동시에 손을 대면 "채점된 내용"과 "사용자가 쓴 내용"이 어긋날 수 있어 제품 판단이 필요하다.
- 선택지:
  - A) **입력창에 `maxLength`** (예: 1,200자) — 장점: 넘치는 글자가 애초에 들어오지 않아 "무엇이 평가됐나"가 화면과 정확히 일치하고, 변경이 화면 두 곳뿐이다. 단점: 붙여넣기가 조용히 잘린다 — 사용자는 글이 잘린 줄 모르고 채점 결과만 본다. 이미 길게 쓰는 사용자는 입력 자체가 불가능해진다.
  - B) **제출 직전 검사 + 카운터**: 입력은 자유롭게 두고, 상한을 넘으면 제출 버튼을 비활성화하고 `N자까지 평가할 수 있습니다(현재 M자)`를 보인다 — 장점: 잘림이 화면에 보이므로 "내 마지막 문장이 평가에서 빠졌다"는 함정이 없다. 사용자가 직접 줄인다. 기존 카운터(`free-writing-tab.tsx:87-89`)를 확장하면 된다. 단점: 검증 코드가 탭 두 곳에 늘고, 저장소 `clip`(400자)과 화면 상한이 다른 값이라 근거를 주석으로 남겨야 한다.
  - C) **`llm.ts`에서 잘라서 전송**(`clipText(text, 1_500)`) — 장점: 화면을 안 바꾸고 자유 작성·번역·추가 질문 세 경로를 한 곳에서 보호한다. 단점: 채점 대상이 조용히 잘린다. "실패를 성공처럼 보이는" 상태를 금지해 온 이 저장소의 원칙(리뷰 2-4)과 같은 모양이다 — 점수는 나오는데 그 점수가 내 글 전부에 대한 것이 아니다.
  - D) **요청 본문 크기 가드**: `messages` JSON이 기준(예: 32KB)을 넘으면 요청을 보내지 않고 한국어 오류 — 장점: 사고성 대량 전송만 막고 정상 사용은 그대로다. 단점: 실제로 긴 글 쓰려는 사용자는 그냥 실패한다. 바이트 기준이라 토큰 비용과 어긋난다.
- 추천: **B를 기본으로, C를 방어선으로** (A는 붙여넣기 조용 잘림 때문에 기각). 이유:
  1. 이 앱의 평가 결과는 사용자가 화면에 쓴 글 전체에 대한 것이라고 이해된다. 잘림이 화면에 보이지 않으면 결과 해석이 거짓이 된다 — B는 그 함정을 없앤다.
  2. 프롬프트 비용은 사용자에게 직접 청구되므로 화면 검증을 우회하는 경로(다른 탭, 앞으로 올 입력창)에도 가드가 남는다 — C를 함께 두면 호출부가 실수해도 안전하다. 단, C는 "잘라서 보내는" 것이 아니라 **기준 초과 시 요청을 멈추는** 형태(D와 절충)로 두는 편이 위 원칙과 맞는다.
  3. 값은 1,000~1,500자 구간을 권한다. evaluation 요청의 `max_tokens`(1,200 — `src/lib/llm.ts:411`)와 짝을 이루고, 저장소 `clip` 400자와는 목적이 다르다(저장소 보호 vs 비용 보호) — 두 수치가 다르다는 근거를 각 자리에 주석으로 남긴다.
- 결정 후 필요한 것: 탭 두 곳의 상한·카운터·제출 차단 검증 테스트, `llm.test.ts`의 본문 가드 테스트(mock fetch의 body 확인), `free-writing-tab.test.tsx`·`translation-tab.test.tsx`에 초과 입력 케이스.
