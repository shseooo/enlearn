### D1-1 파괴적 초기화에 확인 절차를 둘 것인가 (관련: R1-10)
- 위치: `src/components/progress-reset.tsx:112-117`(전체 초기화), `src/components/progress-reset.tsx:158-164`(연습 기록 + 복습 큐)
- 배경: 같은 화면의 "기존 기록을 지우고 대체"는 `window.confirm`을 쓴다(`src/components/backup-card.tsx:178-186`). 그런데 초기화 버튼 두 개는 확인 없이 `resetSeen`/`clearKoreanCache`/`clearLog`/`clearSrs`를 곧바로 부른다. 백업 파일을 만들어 두지 않은 사용자는 클릭 한 번으로 전체 연습 기록·복습 큐·번역 캐시를 잃는다. 현재 코드 기준 세 경로(백업 대체 / 초기화 / 부분 삭제 버튼)의 안전장치가 서로 달라 일관성 문제이기도 하다.
- 선택지:
  - A) 백업 경로와 동일하게 `window.confirm` + "먼저 백업을 내보내세요" 권장 문구
    — 장점: 구현이 같아 일관되고(이미 쓰는 패턴), 코드 최소 변경, 취소 가능. 기존 테스트(`progress-reset.test.tsx`)가 confirm 목으로 확장 가능.
    — 단점: 확인 대화상자는 사용자 습관이 되면 무의미해지고, 모바일·스크린리더에서 확인 경험이 약하다. 삭제 후 되돌리기는 여전히 없다.
  - B) 직전 상태를 잠시 되살리는 undo (삭제는 즉시 하되, 몇 초간 "되돌리기" 안내 표시)
    — 장점: 파괴 동작을 확인 마우스 클릭이 아니라 복구 가능성으로 해결 → 실수 회복률이 가장 높다. 확인 절차가 없는 현행 UX 흐름을 유지한다.
    — 단점: 삭제 직전 상태를 메모리에 보관해야 해 용량·수명 문제가 생기고(전체 초기화는 번역 캐시 포함), 안내 컴포넌트·테스트가 늘어난다. 탭을 닫으면 사라지므로 "보장"이 아니라 "시도"다.
  - C) 현행 유지(확인 없음)를 명시적 정책으로 기록
    — 장점: 앱이 학습자 개인 로컬 데이터에 의존하고, 백업 내보내기가 같은 화면에 있으므로 마찰이 가장 적다.
    — 단점: 회복 수단이 전혀 없다. 화면 상단에 백업 안내(R1-8로 추가된 저장 실패 안내와 같은 자리)라도 두지 않으면 "실수로 다 지움"이 지원 이슈가 된다.
- 추천: **A + (다음 단계로 B)** — 먼저 확인 절차를 백업 경로와 같은 `confirm`으로 통일해 위험을 즉시 낮추고(변경 최소, 일관성 확보), 문구를 "되돌릴 수 없습니다 — 먼저 백업을 내보내세요"로 두어 백업 경로로 안내한다. undo(B)는 별도 과제로 두는 것이 낫다. 상태 보관 설계와 안내 수명(몇 초 / 세션 유지)을 정해야 하고, 이는 이 화면의 UX 방향 결정과 붙어 있다.
- 결정 시 함께 정할 것: 부분 삭제 버튼("동화 기록 지우기", "한국어 번역 캐시 지우기")도 확인을 받을지 — 전체 초기화만 확인하면 "점진적으로 전부 지우기"가 무확인으로 남는다.

### D1-2 큰 저장소의 쓰기 비용을 어떻게 줄일 것인가 (관련: R1-6, R1-7)
- 위치: `src/lib/corpus.ts:201-207`(`markSeen`), `src/lib/corpus.ts:379-397`(`cacheKorean`), 상한 `MAX_SEEN = 20_000` / `MAX_KOREAN_CACHE = 4_000`(`src/lib/corpus.ts:23-24`)
- 배경: 이번 수정으로 **읽기** 비용은 줄었다 — 파싱 결과 재사용(`src/lib/storage.ts:63-90`), 스냅샷의 giant 문자열 비교 제거, 렌더당 읽기 4회 → 2회. 그러나 **쓰기**는 구조상 여전히 저장소 한 축(seen 또는 kocache) 전체를 `JSON.stringify` + `setItem` 한다. 상한까지 채운 상태에서의 한 번의 문장 받기는 약 0.8MB(seen) + 코퍼스 번역 캐시를 다시 쓴다. 리뷰 R1-7의 flaky 테스트도 이 O(n) 쓰기 × n번에서 나왔다(테스트는 벌크 경로로 분리해 해결).
- 선택지:
  - A) 세그먼트 키로 분할 — seen/kocache를 `enlearn.seen.v2.<chunk>` 처럼 여러 키로 쪼갠다
    — 장점: 쓰기 범위를 청크 단위로 줄여 상한에서도 일정 비용. 읽기도 필요한 청크만.
    — 단점: **저장소 키 스키마 변경** → 기존 사용자 데이터 마이그레이션 코드와 버전 키(v3)가 필요하다. 백업 형식·개수 집계·`importSeen`/`importKoreanCache`의 replace/merge 규칙까지 함께 바뀌고, 키 개수 증가로 localStorage 항목 제한(브라우저별)을 새로 고려해야 한다. 롤백 경로도 정해야 한다.
  - B) 쓰기 디바운스/일괄화 — 변경을 메모리에 쌓고 일정 시간·탭 hidden 시점·`pagehide`에 한 번 쓴다
    — 장점: 스키마를 바꾸지 않고, 문장 연속 받기에서의 쓰기 횟수를 크게 줄인다.
    — 단점: 브라우저 강제 종료·크래시 시 마지막 변경을 잃는다. "받은 문장 기록"이 사라지면 같은 문장이 다시 나오는 학습 경험 결함이고, 앱이 백업 수단이 있는 데이터라도 신뢰 수준이 낮아진다. 시점 선택(언제 flush)이 제품 동작 결정이다.
  - C) 상한을 낮추어 유지 — 예: `MAX_SEEN` 20,000 → 5,000
    — 장점: 코드 변경 없음(상수 하나), 저장소 크기가 줄어 현재 읽기/쓰기 경로로 충분.
    — 단점: 3,000/1,400문장 코퍼스 기준 이미 4,400문장 이상을 풀면 예전 문장이 재출제된다 → "한 번 받은 문장은 기록되어 다시 나오지 않습니다"라는 화면 약속(`src/components/translation-tab.tsx:407`)을 바꿔야 한다.
  - D) 현행 유지 — 읽기 최적화(R1-6 조치)로 충분한지 실측으로 확인하고 닫는다
    — 장점: 위험 없음. 실제 사용자는 상한 근처에 도달하기 전에 코퍼스 전체(4,400문장)를 소진한다.
    — 단점: 상한 근처 사용자에게는 체감 지연이 남는다. 이번 리뷰처럼 테스트를 느리게 만드는 원인이 계속 남는다.
- 추천: **D로 확정하되 관측 지점을 하나 남긴다.** 이번 조치로 렌더·읽기 비용은 사라졌고, 쓰기 비용은 "코퍼스 상한(4,400문장)을 모두 푼 사용자"에만 영향을 준다. A(스키마 변경 + 마이그레이션)와 B(데이터 손실 가능성)는 지금 단계에서 감수할 위험보다 크기가 크므로, 실제 상한 도달 사용자에게 지연이 확인되기 전까지는 보류가 합리적이다. 보류 결정이라면 화면에 "기록 N개 / 정리" 안내를 두어 사용자가 스스로 상한 아래로 정리하게 하는 저비용 완충(D의 실행 형태)을 추천한다.
- 결정에 필요한 데이터: 상한 도달 사용자 수(없다 = 개인 앱), 실 측정 지연(상한 채운 환경에서 `markSeen` 1회 시간), 브라우저별 localStorage 한도.
