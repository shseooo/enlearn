- 제안: 성공 본문에서는 자르지 말고 `await res.text()`를 그대로 파싱하고, 화면에 보여주는 조각만 `sanitizeProviderBody(body)`의 `limit`으로 제한한다. 메모리 상한이 필요하면 `res.body` 스트림을 200KB까지만 읽는 식으로 "잘라 읽기"를 하되 파싱 가능한 범위여야 한다. 회귀 테스트: 본문 1,200자인 평가 응답 → `score`/`feedback` 정상 파싱.

### R1-2 [심각] [버그] 요청 중 출처를 바꾸면 `picking`/`loading`이 영원히 켜진 채 남는다 (복구 경로 없음)
- 위치: `src/components/translation-tab.tsx:309` (`requestSeq.current += 1`), `src/components/translation-tab.tsx:235`·`src/components/translation-tab.tsx:277` (`finally { if (!stale()) set…(false) }`)
- 문제: 출처 `<select>`의 `onChange`가 `requestSeq`만 올리고 상태를 정리하지 않는다. 진행 중이던 호출은 `stale()`이 true가 되어 `finally`의 `setPicking(false)`/`setLoading(false)`를 **건너뛴다**. `setPicking`은 193행, `setLoading`은 245행에서 켜는 것 말고는끄는 지점이 그 `finally`뿐이므로 상태가 그대로 남는다.
- 근거: 코드 흐름 — ① `handleGetSentence`(190행)가 `picking=true` → ② 출처 변경(309행)으로 `requestSeq` 증가 → ③ 지연 응답/취소에서 `catch`가 `stale()`로 조기 반환 → ④ `finally`의 `if (!stale()) setPicking(false)`(235행)도 건너뜀. 이후 `canPick = !picking && …`(111행)와 "다시 받기" 버튼(352행)이 모두 비활성화되고, 스피너와 "취소"만 남는다. `cancel()`은 `useCancellable.ts:35-40`에서 이미 빈 컨트롤러라 아무것도 하지 않으므로 **새로고침 전까지 문장 받기가 불가능**하다. 평가 중 출처를 바꾸면 같은 방식으로 `loading`이 고정되어 결과 카드(`!loading && result`)도 사라진다. 기존 테스트(`src/components/__tests__/translation-tab.test.tsx:276-291`)는 저장소·표시만 확인하고 버튼 상태를 확인하지 않는다.
- 제안: `onChange`에서 seq를 올린 뒤 상태를 명시적으로 되돌린다(`setPicking(false); setLoading(false);`), 또는 `finally`의 조건에서 `setPicking/setLoading` reset을 `stale()`과 무관하게 하되 "새 요청이 시작하기 전에만" 적용하도록 `picking`을 seq와 함께 보관한다. 회귀 테스트: 문장 받기 클릭 → 출처 변경 → "문장 받기" 버튼이 다시 활성.
