## 이슈

### R8-1 [중간] [버그] 대체(`replace`) 경로는 키 중복을 정리하지 않아, 같은 문장·같은 날짜가 두 개 남고 통계가 이중 계산되며 복습 큐에서는 같은 문장이 영원히 돌아온다
- 위치: `src/lib/practice.ts:831-841`(`importLog` replace), `src/lib/practice.ts:882-886`(`importSrs` replace) — 대비되는 병합 경로: `src/lib/practice.ts:843-870`, `:887-915` — 계약: `src/lib/types.ts:95-108`
- 문제: 병합 경로는 D2-1대로 "같은 `id|date`(큐는 `id`)는 최신 한 건"으로 접지만, 대체 경로는 `incoming`를 그대로 쓴다. 그래서 **백업 파일 안에 같은 키가 두 개 있으면 두 개가 전부 저장소에 들어간다.**
  1. 기록: 두 행이 남아 `practiceStats`가 같은 문장을 두 번 센다(`total`, `week`, `avgScore`). 그 뒤 같은 문장을 다시 풀면 `findIndex`가 **첫 행만** 교체해서 낡은 행이 계속 집계에 남는다.
  2. 큐: `id`가 같은 항목이 두 개 저장된다. `gradeReview`는 `findIndex`로 하나만 고치므로(`src/lib/practice.ts:506-507`) 나머지 하나는 `due`가 그대로 남아 **복습 탭에서 같은 문장이 지워지지 않고 계속 나온다.**
  3. 개수: 중복이 `stored`로 세어지므로 화면은 "기록 2개"라고 말한다(`trimmed`은 0). `types.ts:98`의 불변식(`stored + merged + trimmed + rejected = 들어온 항목 수`, "replace는 merged 0")도 이 상태에서 어긋난다.
- 근거(임시 vitest 프로젝트로 실측, 저장소 코드 수정 없음):
  ```
  importLog([{id:<실제 id>, date:"2026-01-01", ts:1, answer:"a", score:20},
             {id:<같은 id>, date:"2026-01-01", ts:2, answer:"b", score:90}], true)
    → {"stored":2,"rejected":0,"trimmed":0,"merged":0}, 행 2개
    practiceStats → total=2, avgScore=55   // 한 번의 연습이 두 번 계산됐다
    logPractice(같은 문장) → 행 ["c","b"]    // 첫 행만 갱신, 낡은 "b"가 남는다
  importSrs([{id:"classic:a", stage:0, due:"2026-01-02",…},
             {id:"classic:a", stage:3, due:"2026-03-04",…}], true)
    → 큐 2개, gradeReview("classic:a","forgot") 후에도
      [{due:"2026-11-13"},{due:"2026-03-04"}]  // 둘째가 계속 대기 중이다
  ```
  발화 조건은 "두 백업의 `log`/`srs` 배열을 이어붙인 파일"로, D2-1이 존재하는 이유가 바로 그 작업이다. 테스트는 병합 경로만 고정했다(`src/lib/__tests__/practice.test.ts:501-553`) — `grep "replace"`로 본 대체 테스트(`:694`, `:834`, `:977`, `:1009`)는 전부 서로 **다른** id를 쓴다.
  같은 자리에서 `trimmed`이 음수가 될 수도 있다: 쓰기가 실패하면(`safeSetItem` 실패) `stored = loadLog().length`가 **이전** 저장소 개수라 `trimmed = incoming.length - stored`가 음수가 된다(`src/lib/practice.ts:840`, `:885`, `src/lib/corpus.ts:624`, `:699`). 화면은 `writeFailed`를 먼저 보고 빠져나간다(`src/components/backup-card.tsx:84-93`)지만, `import*`는 공개 계약이라 그대로 노출되는 값이다.
- 제안: 대체도 병합과 같은 키 규칙로 정리한다 — 기록은 `id|date`로 접어 `ts` 최신 한 건, 큐는 `id`로 접어 `lastReviewed` 최신 한 건(`importLog`의 `byIdDate`, `importSrs`의 `byId` 로직을 재사용하고 "기존 값" 대신 빈 맵에서 시작하게 하면 된다). 그 다음 `stored = 접은 결과 중 저장소에 남은 개수`, `trimmed = 상한으로 밀린 개수`로 잡으면 불변식이 두 경로에서 성립한다. 쓰기 실패 시에는 `stored`를 0으로 두고 `trimmed`을 `Math.max(0, …)`로 묶는다. 테스트: (1) 같은 `id|date` 두 건 대체 → 행 1개·`stored 1`·`avgScore 90`, (2) 같은 `id` 두 건 대체 → 큐 1개이고 `gradeReview` 후 대기 0, (3) `setItem`을 터뜨린 상태의 대체 → `stored 0`이고 `trimmed >= 0`.

  ```
  before seen=5 korean=1 log=1
  ```

  (`seen` 섹션이 없어도 `parseBackup`은 통과한다 — `src/lib/backup.ts:173-175`는 `log`·`srs` 중 하나만 배열이면 인정한다.) `importLog([], true)`가 저장소를 비우는 것은 테스트로 고정된 의도된 동작이고(`src/lib/__tests__/practice.test.ts:1039-1051`) 대체 결과 문구에도 "받은 문장 0개"가 뜨지만, 그건 **사건 후**의 문구다.

(B) 없는 섹션은 손대지 않는다 — 부분 복원이 가능해지지만 "대체했다"가 더 이상 전체 대체가 아니다. 어느 쪽이든 확인 문구는 실제로 지우는 것을 말해야 한다. 테스트: 대체 확인 창 문구에 `seen` 관련 단어가 있는지, `seen` 없는 백업 대체 후 `seenCount()`가 어떻게 되는지 한 개씩.

### R8-3 [경미] [버그] 다른 탭 감지의 peer TTL(2×15초)이 브라우저의 배경 탭 타이머 스로틀링보다 짧다 — 배너가 꺼지는 방향으로 낡는다

- 제안: `nextReviewDate` 테스트는 미래 항목을 **두 개** 이상 만들되 삽입 순서를 날짜 순서의 역으로 둔다(예: 21일 뒤 항목을 먼저, 3일 뒤 항목을 나중에) — 그러면 비교함수가 돈다. `isNewerIso`의 `:560` 갈래는 (a) 호출부가 파싱 불가능한 값을 걸러낸다는 사실을 테스트로 고정하고 주석을 "방어 코드 — 현재 진입점 없음"으로 고치거나, (b) 함수를 지우고 호출부의 정규화를 신뢰한다. 같은 검증은 `npm run coverage`의 0회 목록으로 매 라운드 확인할 수 있다.

### R8-5 [경미] [테스트부족] 코퍼스 문장 필터의 거부 갈래 여럿이 테스트에 한 번도 지나가지 않는다 — `hasVerb`를 포함한 규칙이 그대로 바뀌어도 아무도 모른다

- 제안: `corpus-tools.test.ts`에 거부 갈래를 표로 추가한다 — `""`, `"he said hello."`(소문자 시작), `"no terminator"`, `"a, b, c, d, e, f, g, h, i, j, k."`(구두점 과다), `'"one "two "three four five six seven eight nine."'`(따옴표 과다), `"The year 1863 and 1864 were hard."`(숫자 과다), `"She read chapter iii twice and smiled."`(소문자 로마숫자는 잡음이 아니다), 동사 없는 나열문(`"The old man, the long road, the cold wind."` → `hasVerb` 거부). 잡음 필터와 `hasVerb`가 같은 조건문 덩어리에 있으니 한 표로 함께 고정된다.

### R8-6 [경미] [에러처리] 번역 캐시 합치기의 "더 최근 기록이 있어 적용되지 않음" 문구는 그 저장소의 규칙과 맞지 않는다
- 위치: `src/components/backup-card.tsx:111`(단일 문구) — 값이 나오는 자리: `src/lib/corpus.ts:708-717`(`importKoreanCache`의 `merged`), 규칙 정의: `docs/decision/resolved.md` D2-1("번역 캐시(kocache)에는 시각 정보가 없으므로 현행 '기존 값 우선'을 유지한다")
- 문제: `merged` 개수는 네 저장소를 합쳐 하나의 문구로 표시된다. 기록·큐·seen에는 "더 최근 기록이 있어 적용되지 않음"이 맞지만, 번역 캐시에는 시각 비교가 아예 없다(`src/lib/corpus.ts:703-705` — 기존 값 우선). 사용자는 "내 백업의 번역이 더 옛날 것이어서 거부됐다"고 읽고, 실제로는 **어떤 번역도 백업의 것으로 바꿀 수 없다**는 사실을 놓친다(더 새로운 사본을 만들어 와도 같은 문구가 뜬다).
- 근거: `src/lib/corpus.ts:716`(`merged: Object.keys(incoming).length - won.length`)의 `won`은 "아직 없던 키"일 뿐이고(`:710`), 비교 시각은 쓰이지 않는다. 화면에는 `backup-card.tsx:108`의 "번역 캐시 N개"와 같은 줄에 이 문구가 함께 뜬다.
