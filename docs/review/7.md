## 이슈

### R7-1 [중간] [버그] `ImportResult.stored`/`trimmed`가 "받아들여진 개수"가 아니라서, 병합에서 밀린 항목은 합친 것처럼 보이고 중복 항목은 "상한으로 제외"로 잘못 표시된다
- 위치: `src/lib/practice.ts:819-828`(`importLog` 병합), `:857-863`(`importSrs`), `src/lib/corpus.ts:588-596`(`importSeen`), `:644-650`(`importKoreanCache`) — 라벨: `src/components/backup-card.tsx:107-108` — 계약: `src/lib/types.ts:97-101`
- 문제: 두 방향으로 어긋난다.
  1. **진 항목이 stored에 들어간다.** `stored`는 키가 저장소에 "존재"하는지로 세므로, D2-1 병합에서 기존 값(더 최근 시각)이 이겨 **아무것도 적용되지 않은 항목**도 합친 개수에 들어간다. 오래된 백업을 합치면 화면에 `기록 300개 … 을(를) 합쳤습니다`가 뜨지만 실제로는 0건이 적용됐다(리뷰 2-4가 금지한 "실패를 성공처럼 보이는" 형태가 D4-2 문구로 되돌아왔다).
  2. **중복 항목이 `trimmed`로 잡힌다.** `incoming` 안에 같은 `id|date`가 두 개면 병합 후 키는 하나만 남으므로 `trimmed = incoming.length - stored`에 잡히고, 화면은 `N건은 저장소 상한으로 제외`(`backup-card.tsx:107`)라고 말한다. `MAX_RECORDS`(2,000)와 무관한 사안인데 사용자는 "저장소 상한"을 읽고 기록을 지워버릴 이유가 생긴다. `types.ts:101`의 doc("저장소 상한 … 으로 잘린 항목 수")과 런타임 값이 어긋난다.
- 근거:
  ```ts
  // src/lib/practice.ts:824-828
  const wanted = new Set(incoming.map((r) => `${r.id}|${r.date}`));
  const stored = loadLog().filter((r) => wanted.has(`${r.id}|${r.date}`)).length;
  return { stored, rejected, trimmed: incoming.length - stored };
  ```
  재현(코드로 확인): `importLog([{id:"x",date:"2026-01-01",ts:1,…},{id:"x",date:"2026-01-01",ts:2,…}])` → `stored:1`, `trimmed:1`(저장소에는 1건만 있고 상한과 무관). `src/lib/__tests__/corpus.test.ts`의 D2-1 테스트 주석 `expect(result.stored).toBe(2); // 두 항목 모두 저장소에 있다`가 이 semantics를 그대로 드러낸다 — 그 중 한 항목은 값이 적용되지 않았다.
- 제안: 세 값을 분리한다 — `stored`(실제로 저장소에 새로 들어간 항목 = 키 존재가 아니라 **값이 들어온 값**인 것), `merged`(병합에서 기존 값이 이겨 적용되지 않은 항목), `trimmed`(정말로 상한으로 잘린 개수 = `incoming.length - 쓴 개수 - 중복`). 최소한 화면은 "N건은 저장소 상한으로 제외"와 "N건은 더 최근 기록이 있어 적용되지 않음"을 구분해야 한다(D2-1의 "합치기는 더 최근 기록을 남깁니다" 안내와 D4-2의 목적이 같은 자리에서 함께 지켜져야 한다). 테스트: (1) 기존 값이 이기는 병합에서 `stored`(적용 개수)가 0이고 화면에 "적용되지 않음" 문구가 뜨는지, (2) 같은 `id|date` 두 건을 준 병합에서 `trimmed`이 0인지(`src/lib/__tests__/practice.test.ts`).

### R7-2 [경미] [버그] seen 병합은 시각으로 비교하는데 상한 트림은 여전히 문자열 순서로 버린다 — 시간대 표기가 다르면 살아남아야 할 최근 기록이 먼저 밀려난다

- 문제: 이번 사이클에 병합 판정을 "문자열 비교 대신 `Date.parse`"로 고치면서(`corpus.ts:517-521`의 근거 주석: "저장된 값에 `+09:00` 같은 오프셋이 들어올 수 있고") 트림은 옛 방식 그대로다. `normalizeSeenValue`(`:549-557`)는 `^\d{4}-\d{2}-\d{2}T` 접두와 40자 이내면 **오프셋이 달린 값을 그대로 통과**시킨다. 그래서 seen이 `MAX_SEEN`(20,000)에 닿아 트림이 일어나는 순간, `2026-06-01T00:00:00+09:00`(실제 시각 2026-05-31T15:00Z)는 `2026-05-31T16:00:00Z`보다 사전순으로 뒤라 "최근"으로 오해되어 살아남고, 진짜 최근 항목이 버려진다.
- 근거: 두 저장소 경로의 비교 기준이 코드 두 곳에서 다르다(위 라인). 같은 이유로 리뷰 3-6에서 `normalizeSeenValue`가 도입됐고, 그 논의를 따라간 것이 `isNewerIso`인데 트림만 남았다.
- 제안: `trimSeen`도 `Date.parse` 기준으로 정렬하되, 파싱 실패 값은 가장 오래된 것으로 본다(`isNewerIso`의 규칙과 동일하게 유지). 오프셋이 섞인 seen 맵을 만들어 20,000건을 채운 뒤 어느 키가 남는지를 보는 테스트 한 개. (비용은 `MAX_SEEN` 크기 정렬 한 번으로 이미 존재하는 동작과 같다.)
