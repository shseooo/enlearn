## 이슈

### R2-1 [심각] [버그] 배치 번역 파서가 0-based 번호 목록에서 항목마다 기준을 다르게 적용해, 엉뚱한 문장에 번역을 붙이고 조용히 코퍼스·캐시에 남긴다
- 위치: `src/lib/parse-batch.ts:86-110` (핵심은 `src/lib/parse-batch.ts:92`), 소비자 `scripts/build-corpus.mts:605-613`(`cache[normalizeKey(e.en)] = …` → `public/data/corpus/classics.json`)
- 문제: `index = n >= 1 && n <= expected.length ? n - 1 : n`은 **항목마다** 1-based/0-based를 판정한다. 모델이 0-based로 답하면 첫 항목(`i:0`)만 `index=0`으로 맞고, `i:1`은 `index=0`(이미 있으므로 `src/lib/parse-batch.ts:110`에서 버려짐), `i:2`는 `index=1`… 즉 **두 번째 항목부터 한 칸 어긋난 번역이 붙는다.** 코드 주석은 "엉뚱한 번역이 붙으면 코퍼스에 영구로 남는다"(`src/lib/parse-batch.ts:99`)를 막겠다고 선언하지만, 이 경로는 그 판정을 거치지 않는다.
- 근거: 실제 재현(코드 수정 없음, 파서만 import)
  ```
  node --input-type=module -e "const {parseTranslationBatch}=await import('$PWD/src/lib/parse-batch.ts');
  const ENS=['Alpha sentence one.','Beta sentence two.','Gamma sentence three.'];
  const m=parseTranslationBatch(JSON.stringify({items:[{i:0,ko:'알파 문장입니다.'},{i:1,ko:'베타 문장입니다.'},{i:2,ko:'감마 문장입니다.'}]}),ENS);
  for(const [k,v] of m) console.log(k,'=>',v.ko);"
  # Alpha sentence one. => 알파 문장입니다.
  # Beta sentence two.  => 감마 문장입니다.     ← 엉뚱한 번역
  ```
  손실은 여기서 끝나지 않는다. `fillKoreanTranslations`는 그 결과를 `.corpus-cache/translations.json`에 `normalizeKey(en)` 키로 저장하고(`scripts/build-corpus.mts:612`), 다음 빌드는 그 캐시를 검증 없이 재사용한다(`scripts/build-corpus.mts:573-582`). 사람이 옮긴 1,400문장 번역이 들어 있는 같은 파일을 `--llm` 빌드가 오염시킬 수 있다. `audit-translations.mts`의 "중복 번역" 검사(`scripts/audit-translations.mts:92-96`)는 어긋남을 잡지 못한다(번역이 서로 달라지므로). 기존 테스트(`src/lib/__tests__/parse-batch.test.ts:23-29`)는 항목 1개짜리 0-based만 확인해 이 어긋남을 잡지 못한다.
- 제안: 배치 **전체**에 대해 기준을 한 번만 정한다. 항목 번호 집합이 `{0..n-1}`이면 0-based, `{1..n}`이면 1-based로 해석하고, 두 기준이 섞여 있으면(예: 0과 n이 동시에 나타남) 그 배치를 통째로 폐기한다. 자릿수 추측처럼 "자리가 이쯤이니"는 금지하고, 폐기 사유를 로그에 남긴다. 회귀 테스트: 0-based 3항목 → 세 문장에 각각 올바른 번역 / 1-based·0-based 혼합 → 0건.
