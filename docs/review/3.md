### R3-1 [심각] [버그] 코퍼스 빌드가 원본을 하나도 받지 못한 상태에서 사람 손으로 옮긴 1,400문장을 `classics.json` 빈 파일로 조용히 덮어쓴다 (exit 0)

- 근거: 실제 재현
  ```

    ✗ 이상한 나라의 앨리스: 캐시에 없음(--offline): pg11.txt        (×14)

      📖 동화 명문장: 0문장 — 쉬움 0 / 보통 0 / 어려움 0

  $ cat $TMP/public/data/corpus/classics.json
    {"lane":"classic", … ,"sources":[],"entries":[]}
  ```
  같은 상태에서 `node scripts/audit-translations.mts`는 `코퍼스 0문장 · 누역 0 · 빌드 미반영 0 …` → **"감사 통과"(exit 0)**를 출력한다. 결과로 앱은 빈 코퍼스를 정상 파일로 받아들인다(`isCorpusFile`은 빈 배열을 통과시킨다, `src/lib/corpus.ts:80-86`) → `pickEntry`가 null을 돌려 화면에는 "이 조건에 맞는 문장이 코퍼스에 없습니다"(`src/components/translation-tab.tsx:156`)가 뜬다. daily 레인은 내려받기 실패가 예외로 전파되어(`scripts/build-corpus.mts:688-699`) 쓰기가 일어나지 않는다 — classic만 이 경로다. 코드에 이미 "요청하지 않은 레인의 파일을 빈 내용으로 덮어쓰지 않는다"(`scripts/build-corpus.mts:858-863`)는 방어가 있으므로, 실패한 레인에 대한 방어가 의도적으로 빠진 것은 아니다.
- 제안: ① 쓰기 직전에 " 수록 0개면 쓰지 않고 exit 1", 이전 파일 대비 급감(예: 50% 이상)하면 `--force` 없이는 거부. ② 내려받기 실패가 1개라도 있으면 마지막에 실패한 권 수를 요약 출력하고 exit 1로 끝낸다(재시도/`--offline` 안내와 함께). ③ `audit-translations.mts`는 `corpus.entries.length === 0`(또는 기대 개수 대비 급감)을 오류로 본다. ④ 회귀 테스트: `--offline` + 캐시 없음 → 기존 `classics.json` 내용이 그대로 + exit 1.

### R3-2 [중간] [버그/에러처리] merge-translations.mts의 "행 번호" 안전장치는 어긋남을 잡지 못하고, 번호 없는 원고는 검사조차 하지 않는다
- 위치: `scripts/merge-translations.mts:110-119`(번호 확인), `scripts/merge-translations.mts:70-74`(번호 없는 줄 → `rowNumber: null`), `scripts/merge-translations.mts:103-107`(`.filter(Boolean)`가 빈 줄을 지움), `scripts/merge-translations.mts:129-147`(실제 대응은 `offset + i`), `scripts/dump-untranslated.mts:27-30`(행 번호 = 자기 인덱스)
- 문제 (1) 번호가 없으면 무검사: `line.rowNumber === null`이면 확인을 건너뛴다("번호 없는 원고는 순서만 믿는다"). 그런데 `filter(Boolean)`이 빈 줄을 지워 버리므로, 원고 중간 빈 줄 한 줄이 순서를 밀어도 번역이 한 칸 어긋난 채로 조용히 캐시에 들어간다. 탭 대신 공백을 쓴 줄(`^(\d+)\t` 불일치)도 같은 경로로, 줄 번호가 번역 텍스트에 붙은 채 저장된다.
- 근거: 실제 재현 (worklist 3행, 원고 중간 빈 줄 1개, 번호 없음)
  ```
  $ printf '0\tOne sentence here.\n1\tTwo sentence here.\n2\tThree sentence here.\n' > .corpus-cache/worklist.tsv
  $ printf '첫 문장 번역입니다.\n\n세 번째 문장 번역입니다.\n' > mss.txt
  $ node scripts/merge-translations.mts mss.txt#0
    mss.txt +2줄 (작업 목록 1~2)
    캐시 합침: 신규 2 · 갱신 0 · 건너뜀 0 — 캐시 2항목 …
  EXIT=0
  $ cat .corpus-cache/translations.json
    {"one sentence here":{"ko":"첫 문장 번역입니다.",…},
     "two sentence here":{"ko":"세 번째 문장 번역입니다.",…}}   ← 어긋남, 경고 없음
  ```
- 문제 (2) 번호가 있어도 구조적으로 못 잡는다: 검사는 `rowNumber === offset + i`뿐이고 실제 대응도 `offset + i`로 이뤄진다. `dump-untranslated.mts`는 행 번호를 자기 인덱스로 쓰므로 어떤 worklist에서든 "번호 = 위치"가 항상 성립한다. 따라서 dump → 원고 작성 → **코퍼스 재빌드(worklist 재생성)** → merge 순서에서, 원고가 옛 worklist의 500~599행을 옮긴 것이라도 새 worklist의 `#500` 구간과 번호가 맞아떨어져 통과한다. 헤더가 약속하는 "번호가 한 줄이라도 어긋나면 파일 전체를 거부한다"(`scripts/merge-translations.mts:12`)가 실제로 잡는 것은 원고 내부의 자체 어긋남뿐이다. 3차 리뷰 R3-12가 남긴 "원고 줄 단위 교차 검증은 사람이 무작위 표본으로 확인" 상태가 그대로다.
- 제안: ① 번호 없는 원고를 거부한다(형식이 헤더에 이미 강제돼 있다). ② 원고 줄을 `번호\t원문 앞 단어\t번역`로 받아 worklist 행의 `en`과 대조한다 — `scripts/dump-untranslated.mts:30`이 이미 원문을 내보낸다. ③ 최소한 merge가 worklist 지문(줄 수 + `normalizeKey(en)` 목록 해시)을 `.corpus-cache/worklist.meta.json`에 저장하고, 원고 인자에 선언된 worklist와 불일치하면 거부한다. ④ 테스트: (a) 번호 없는 원고 + 빈 줄 1개 → 거부(exit ≠ 0), (b) worklist 재생성 후 어긋난 원고 → 거부.

(D1-2는 "큰 저장소의 쓰기 **비용**" 결정이고, 여기는 "동시 쓰기의 **손실**"이라 별개다.)
